# Codebase Audit — 2026-03-25

Covers changes introduced around team ownership, SLA tracking, and vulnerability instances (commits up to `c65f6dc`).

---

## Critical

### 1. Timezone crash in team dashboard
**File:** `backend/app/routers/teams.py:254`

`datetime.utcnow()` returns a naive datetime, but `first_seen_at` is timezone-aware. Comparing them raises `TypeError: can't subtract offset-naive and offset-aware datetimes` at runtime — the team dashboard crashes whenever any vulnerability instances exist.

**Fix:** Change to `datetime.now(timezone.utc)` and ensure `timezone` is imported.

---

### 2. N+1 queries in list endpoints
**Files:** `routers/scans.py`, `routers/reports.py`, `routers/teams.py`

Accessing `.findings`, `.registry`, `.team` inside loops triggers one query per scan per relationship. A 20-scan page executes ~61 queries instead of 1.

**Fix:** Use SQLAlchemy eager loading:
```python
from sqlalchemy.orm import joinedload
scans = db.query(Scan).options(
    joinedload(Scan.findings),
    joinedload(Scan.registry),
    joinedload(Scan.team)
).all()
```

## High

### 3. Undefined variable in scan error handler
**File:** `backend/app/tasks/scan.py:241`

The catch-all exception handler references `scan_repo`, which is not defined at that scope. Error recovery itself throws `NameError`, leaving scans permanently stuck in a non-terminal state.

---

### 4. SLA settings parsed without validation
**File:** `backend/app/routers/teams.py:199-201`

```python
critical_min = float(settings.get_value("sla_cvss_critical_min", default="9.0"))
```

No try/except around `float()` — a non-numeric setting value crashes the team dashboard. There is also no server-side validation on the settings write path, so invalid values can be stored via direct API calls.

---

### 5. Team ID not preserved on scan rerun
**File:** `backend/app/routers/scans.py:218-228`

Rerun copies `registry_id` and `scanner_override` but omits `team_id`. Re-assignment via `resolve_team_for_target()` in the task may assign to a different team if ownership rules have changed since the original scan.

---

### 6. Policy deletion causes orphaned results
**File:** `backend/app/models.py`

`PolicyResult` stores only a `policy_id` FK, not the policy action or name at time of evaluation. If the policy is deleted, historical results lose their context — the UI cannot show what policy was evaluated or what its action was.

**Options:**
- Soft-delete policies (add `deleted_at` column)
- Snapshot policy content into `PolicyResult` at evaluation time
- Cascade-delete `PolicyResult` rows when a policy is deleted

## Medium

### 7. Broad `except Exception: pass` in scan task
**File:** `backend/app/tasks/scan.py:63-68`

Silently swallows all errors, including programming bugs. Makes production debugging extremely difficult. Already flagged in `backend/app/CLAUDE.md` as known tech debt — narrow when touching these areas.

---

### 8. Race condition in vulnerability instance upsert
**File:** `backend/app/repositories/repos.py:264-322`

Classic TOCTOU: existence check then insert/update in separate statements. With 3 Celery worker replicas scanning the same target concurrently, duplicate rows can be created.

**Fix:** Use a DB-level upsert (`INSERT ... ON CONFLICT UPDATE` for SQLite/PostgreSQL).

---

### 9. Frontend/backend type mismatches
**Files:** `backend/app/schemas.py`, `frontend/src/types.ts`

- `ScanRead` schema exposes both `finding_count` and `findings_count` (duplicate fields, noted as a compatibility workaround)
- `TopVulnerability` includes `max_cvss` in the backend schema but it is absent from the `types.ts` definition — TypeScript will not surface it even though the backend sends it

---

## Security

### 10. Registry credentials stored in plaintext
**File:** `backend/app/models.py:42-43`

`username` and `password` are stored unencrypted in SQLite. At minimum, passwords should be encrypted at rest. Prefer environment variables or a secrets manager for production deployments.

---

### 11. No validation on scan `target` field
**File:** `backend/app/routers/scans.py`

The `target` value is passed to subprocess scanner invocations. SQLAlchemy parameterization prevents SQL injection, but an unsanitized target could cause command injection if it reaches a shell.

**Recommended constraint:**
```python
target: str = Field(..., pattern=r'^[a-zA-Z0-9._/:@-]+$')
```

---

### 12. CORS defaults to `"*"`
**File:** `backend/app/main.py`

If deployed without setting `ALLOWED_ORIGINS`, the API accepts requests from any origin. The default should be a restrictive value; `"*"` should require an explicit opt-in.
